## 项目定位

这条链路是一台真实工作站：FR3 机械臂、Pika 夹爪、两颗 RealSense（腕部 `ee` 与侧视 `side`，60 Hz）。目标是把它从“能录能训”推进到一条可以重复执行的闭环：采集 → 数据集 QC → Training View → ACT / pi0.5 训练 → 离线验证 → 真机 preview → 真机 bounded rollout。

这个项目对外最有价值的部分，不只是“能让一个 policy 在 FR3 上跑起来”，而是把机器人学习里最耗时间的几件事系统化：场景怎么恢复到可比状态，失败怎么在 rollout 刚结束时被结构化记录，落点怎么和 demo 覆盖分布放在同一张 base-frame 图里读，checkpoint 能不能安全上机怎么在启动前 fail fast。它把一次次手工调试，收敛成一套能让团队更快迭代、更容易交接、更容易复盘的实验基础设施。

真正花掉时间的不是某个模型，而是**合同**：数据集里被记录的物理量、训练时被重建的动作、推理时被送进网络的观测，必须逐字对应同一件事。所以这个项目的主要贡献，是把这些合同做成 GUI、manifest、preflight、测试和日志，让团队在训练前、上机前、rollout 后都能快速判断问题在哪里。

一条贯穿全程的纪律：不把另一台 rig（DAS / Hikrobot）的经验参数迁移到这台机器上。调参只在本 rig 上发生。

## 面向效率的 GUI 能力

这套 GUI 的设计目标是缩短机器人学习里最昂贵的循环：从一次失败 rollout，到知道下一轮应该补数据、调动作空间、修感知合同、还是排查硬件。它把“实验员脑子里的上下文”落成界面状态和日志，而不是散落在终端历史、视频文件名和临时笔记里。

| 能力 | 第一性原理 | 对学习效率的影响 |
| --- | --- | --- |
| Checkpoint 合同检查 | 上机前先判断 checkpoint 的 dataset、action mode、tool frame、camera keys、crop 与 rig 是否一致 | 避免把错误 checkpoint 跑成“模型不行”的假结论 |
| 交互式 rollout 控制 | policy reload 很慢，场景和 arm start 又必须可比，所以运行进程应保留，Start / Stop / Move to start 走同一控制通道 | 同一 checkpoint 可连续跑多次，不用反复重启推理和相机 |
| 场景恢复 | policy 只在 demo 覆盖分布里有意义；reset 目标必须在 base x/y 上表达，并从 demo release 点推 pick pose | 每次 rollout 后快速把 peg 放回可控区域，让批量评估可比 |
| 阶段评分 | success / failure 只有一 bit，不能告诉你失败发生在接近、接触、获取、转移还是插入 | 训练迭代直接看最大漏斗掉点，而不是猜下一轮修哪里 |
| 落点散点图 | 成功率回答“多少次”，几何图回答“错在哪里”；落点必须和 demo grasp / release 分布同坐标系 | 一眼区分数据覆盖问题、系统性偏移、夹爪未闭合和任务末端精度问题 |
| Rollout history | checkpoint 会被清理，但它的实验记录仍决定下一轮取舍 | 让客户、团队或投资人看到迭代证据，而不是只看一次 demo |

这里最关键的取舍是：不把 rollout 后的评分做成一个主观平均分。GUI 使用 task ladder，把任务拆成共享阶段词表：未接近、接近、接触、获取、转移、目标接触、约束满足、释放稳定。成功由阶段推出，blocker 单独记录，aborted 不进入成功率分母。这样 20 次全失败的 rollout 仍然能产出信息：到底是 20 次都没碰到物体，还是多数已经抓起、只是在插入阶段掉下去。

落点图同样遵循这个原则。每个 rollout 的 `graspXyz`、`releaseXyz`、`approachXyz` 存在 append-only JSONL 里；页面只把当前 checkpoint 的点画在图上，底层叠加同一训练 dataset 的 demo grasp / release landmarks。空心点表示夹爪没闭合，颜色表示阶段，虚线环表示 demo 曾经覆盖过的抓取半径。它不是好看的可视化，而是用来回答一个具体问题：这次失败是在训练分布外，还是 policy 在分布内产生了系统性偏差。

场景恢复功能把这个闭环接上了执行层。GUI 从 demonstration 的 release 均值估计 hole / pick pose，操作者在桌面 base x/y 图上刷允许区域；相机 still 不是简单拉伸成背景，而是按 table plane 投影到同一个 base-frame window，再由 runtime 在两次 rollout 之间移动 FR3 和夹爪，把 peg 放到采样点。这样每一轮试验开始前，任务分布是被显式控制的。

## 先冻结坐标系和起始位姿

在讨论任何精度问题之前，两件事必须先冻结，否则后面所有实验都不可比。

**起始位姿只有一个来源。** 闭环以 `fr3_pika_gripper.xml` 的 `home` keyframe 作为唯一初始 pose 合同（前 7 个 arm qpos 为 `0 -0.785 0 -2.355 0 1.57079 0.785`），录制与 rollout 走同一个 helper，执行后读回 `state.q` 逐关节校验，并在日志里打印 keyframe 名和 q target。SDK 自带的 `move_to_start()` 不是工作站合同。

**IK 目标帧必须从几何合同推出。** 训练动作代表的是手指工作点，不是 gripper mount，所以 IK 目标是 `pika_task_tcp`；URDF、MJCF、录制 config、rollout 参数必须同名同位姿，并由 frame contract test 锁住（`pika_task_tcp` 平移误差 ≤ 1 mm、旋转误差 ≤ 0.1°）。runtime 默认值不参与表达合同——不显式传参时 Pika 会落到 `pika_gripper_ee`，这个默认值在这台机器上是错的。

第一性原理是同一句话：**policy 的动作目标必须对应数据集里被记录、被重建的那个物理点**。如果 IK 用的是 gripper mount 或另一个固定 frame，系统不会报错，只会把整条轨迹平移到错误的工作空间。

## QC gate 与 Training View

数据集进训练前必须过 QC。`qc_pass` 直通；`qc_warn` 必须显式确认并把豁免写进 event log；其他状态一律拒绝并指向 Dataset Processing 页面。前端 Training View 的每一行直接显示 QC 状态、禁用原因和具体 warning，`/api/datasets/export` 透传 `acknowledge_warnings`，让“这条数据能不能进训练”成为界面上读得出来的判断。

Training View 离线派生训练动作合同：默认 `delta_ee_from_prev_cmd`，保留 `absolute_ee` 作为诊断基线；`meta/il_view_manifest.json` 记录 action contract、自检结果、excluded episodes 和 source episode map。跨 session 合并只走 CLI，且每个源 session 都必须先过 QC。

## 训练与上机诊断能力

这个项目里沉淀了一组可复用的诊断能力，用来把“模型没学会”拆成更具体的工程问题。

- 观测合同：Training View 的 camera crop、feature shape、实时相机输入和 step0 dump 走同一套 manifest 对账。
- 相机合同：录制和推理侧的曝光、增益、fps 被显式记录，避免上机时切回自动曝光造成分布漂移。
- 动作合同：action mode、tool frame、gripper 单位和归一化统计在 checkpoint 上机前被检查，而不是等 rollout 行为来暗示。
- 数据合同：QC 状态、warning acknowledgement、excluded episodes 和 source episode map 都写进可审计产物。
- 训练反馈：通过动作统计、梯度范数和 early-stop 判据，尽早发现“训练在优化错误信号”的情况。

这类能力对外展示时比单个实验结果更重要：它说明我能搭的不只是 demo，而是一套持续产出可靠实验结论的机器人学习基础设施。

## 上机运行与交付形态

rollout 侧按风险分层：`env` 打印环境快照，`smoke` 验证 checkpoint / 相机 / forward / action decode，`preview` 做短步数预演，`real_once` 做单次 bounded rollout，`interactive` 支持连续 Start / Stop / Move to start，`real_debug` 叠加 MuJoCo target viewer。所有会移动机器人的路径都有 motion confirmation、合同检查和日志落盘。

运行中页面直接显示 policy 实际看到的相机帧、step limit、leash、tool frame、rollout index、trace path 和 full log。失败后马上进入评分与归因，而不是等人回看视频、翻终端、再凭记忆补记录。

场景恢复、落点图和评分系统组合在一起后，工作流变成：选择 checkpoint → 上机合同检查 → 连续 rollout → 现场评分 → 看落点分布 → reset 场景 → 下一次 rollout。它让机器人学习从一次性展示，变成可批量运行、可比较、可复盘的实验循环。

## 对外价值

这套工作站能力适合三类合作场景：

- 对客户：把具身智能原型从“能跑一次”推进到“能定位失败、能稳定迭代、能交付现场工具”。
- 对合伙人：提供从硬件接入、数据采集、训练视图、策略部署到 real-robot evaluation 的完整工程闭环。
- 对投资人：展示的不只是单次机器人演示，而是让机器人能力持续提升的底层系统能力。

我的优势在于把模型、数据、硬件和调试界面放到同一条链路里思考。机器人学习真正需要的是缩短每一轮试错的周期，并让每一次失败留下足够的信息，指导下一轮该修哪里。
